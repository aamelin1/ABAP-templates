# База знаний SAP — архитектура

Статус: концепт, итерация 2026-07-22 (v3: + структура репозитория и формат заметки).
Владелец: Андрей Амелин (aamelin1).

## Принципы

1. **Git — единственный source of truth.** Репозиторий `aamelin1/sap-kb` (публичный, вычищен от специфики работодателя). Всё остальное — кэши, которые можно снести и пересоздать.
2. **Чтение и запись — разные контуры.** Чтение публичное и без аутентификации; запись идёт локально через git и не касается MCP вообще.
3. **Зависимости — только крупные вендоры или собственный код.** GitHub (raw, Actions), Anthropic (Claude Code, web_fetch). Хостинг в v1 отсутствует. Проекты энтузиастов в стек не входят.
4. **Один писатель.** Базу пополняет только владелец; конфликты git исключены по построению.
5. **Ни одно оглавление не ведётся руками.** llms.txt и оглавление README генерируются одним скриптом из frontmatter заметок.

## Структура репозитория — ✅ зафиксировано

```
sap-kb/
├── README.md            # для людей: описание + оглавление (оглавление генерируется)
├── llms.txt             # для ИИ: индекс с raw-URL и keywords (генерируется)
├── LICENSE              # MIT
├── docs/
│   ├── KB-ARCHITECTURE.md    # этот документ
│   └── NOTE-TEMPLATE.md      # шаблон заметки + правила заполнения keywords
├── tools/
│   └── build_llms_txt.py     # генератор llms.txt и README-оглавления
├── .github/workflows/
│   └── build-llms-txt.yml    # Action-страховка генерации
├── 10-fi/                    # разделы по модулям/назначению
│   ├── f110-setup-and-errors.md
│   └── img/                  # картинки раздела (не общая свалка)
├── 20-fi-aa/  30-co-ml/  40-mm/  50-abap/  60-basis-tools/
├── 70-reference/  80-blog/
└── 90-source-code/           # ABAP-исходники
```

### Правила

- **Имена файлов и папок**: латиница, lowercase, дефисы (`f110-setup-and-errors.md`, `10-fi`). Без пробелов и кириллицы — чистые raw-URL.
- **Лицензия**: MIT.
- **Одна заметка = один файл = одна тема**, размер, читаемый целиком (~до 300–500 строк).
- **Два оглавления, один источник**: llms.txt (raw-URL + keywords, для ИИ) и оглавление в README.md (относительные ссылки, без keywords, для людей/Obsidian) генерируются одним скриптом. Папочные `00_Index.md` упраздняются.
- **Исходники ABAP**: у каждого файла в `90-source-code` должна быть заметка-владелец, ссылающаяся на него через поле `source`. Сиротский код в оглавления не попадает. Метаданные в самих ABAP-файлах не ведутся.
- **Картинки** — только для людей (web_fetch их не читает): суть заметки — текстом, скриншот — иллюстрация. Лежат в `img/` своего раздела; внешние вложения (URL на GitHub-attachments) при миграции затягиваются в репо.
- **`.gitignore`**: `.obsidian/`, `.DS_Store` — конфигурация вьюера не утекает в публичную репу.
- **Стабильность URL**: реорганизация (переименование папок/файлов) выполняется одним коммитом один раз, до раздачи внешних ссылок.
- **Чистка наследия** при реорганизации: `README 2.md` → становится основным README.md (отредактировать по правилам выше); `_SOURCES.md` → удалить; заметки-заглушки `(to do)` → `status: todo`; метки «(перевести)» / «⚠️ Черновик» → `status: draft`.

## Формат заметки — ✅ зафиксировано (детали в NOTE-TEMPLATE.md)

YAML-frontmatter + человекочитаемый текст. Поля:

| Поле | Обяз. | Назначение |
|---|---|---|
| `title` | да | Название, понятное вне контекста папки; текст ссылки в оглавлениях |
| `keywords` | да | Поисковый индекс строки llms.txt: транзакции, таблицы, программы/ФМ/классы/BAdI, номера ошибок и SAP Notes, термины парой RU+EN. Ориентир 5–15 ключей |
| `status` | да | `ok` → в llms.txt; `draft` → в llms.txt с пометкой; `todo` → не попадает |
| `summary` | нет | Одна фраза о содержании; если есть — идёт в строку llms.txt перед keywords |
| `source` | нет | Относительные пути к ABAP в `90-source-code`; генератор дописывает их raw-URL в строку llms.txt |

Чего в формате сознательно нет: `module` (выводится из папки), `tags` (слился бы с keywords), даты (знает git), `lang` (keywords двуязычные).

Файлы без frontmatter: генератор берёт title из первого H1, описание пустое, и включает файл в отчёт «неразмеченные» — llms.txt работает сразу, миграция ленивая (трогаешь заметку — размечаешь; массовую разметку может предлагать Claude Code с обязательной вычиткой).

## Контур записи — ✅ зафиксировано

Запись в базу — работа с локальной папкой на маке, синхронизированной с GitHub. MCP для записи не используется.

### Основной путь

1. **Редактор — Claude Code** с папкой базы как рабочей директорией.
   Сценарий: «добавь заметку про <кейс> в раздел 10 FI» → Claude Code создаёт md-файл по NOTE-TEMPLATE.md и запускает `tools/build_llms_txt.py` (обновляются llms.txt и README-оглавление).
   Ручное редактирование (Obsidian и т.п.) равноправно — это обычные файлы.
2. **Транспорт и ревью-шлюз — GitHub Desktop.**
   Push выполняет только человек, предварительно просмотрев diff. Это последний рубеж санитизации перед публичной репой.
3. **Ветки/PR не используются.** Прямые коммиты в `main`.

Claude Code может делать локальные `git commit`; `git push` остаётся ручным осознанным действием.

### Резервный путь (не с мака)

Веб-редактор github.com или мобильное приложение GitHub. Оглавления при этом актуализирует GitHub Action.

### Дисциплина

- **Пушить сразу после правки, не копить.** Незапушенная заметка для ассистентов не существует.
- Перед push — взгляд на diff: «нет ли здесь чего-то, чему не место в публичной репе».

## Контур чтения — ✅ зафиксировано: llms.txt + web_fetch (без хостинга)

Чтение строится на статике в самой репе и штатном инструменте загрузки URL у ассистента. Своего сервера и хостинга нет.

### Механика

1. **`llms.txt`** в корне: H1 + blockquote с инструкцией для ассистента + секции по разделам, строки вида `- [title](абсолютный raw-URL): summary — keywords · код: [файл](raw-URL)`.
2. URL корневого `llms.txt` прописан в **user preferences** каждого используемого аккаунта Claude: «при вопросах по SAP сначала загрузи <URL>, найди релевантные заметки и загрузи их по ссылкам».
3. Ассистент работает **навигацией вместо поиска**: fetch оглавления → матч вопроса о строки описаний → fetch нужных заметок целиком (без чанкинга).

### Требования, вытекающие из механики web_fetch

- Инструмент загружает только URL, уже появившиеся в разговоре. Поэтому: входной URL — явно в preferences; все ссылки в `llms.txt` — полные абсолютные raw-URL.
- Промах навигации возможен только если ответ есть в теле заметки, но не отражён в её строке — лечится дисциплиной keywords.
- `llms-full.txt` не используется (адресная навигация лучше частичного чтения гигафайла).

### Генерация

- `tools/build_llms_txt.py`: обходит `*.md` разделов, парсит frontmatter, собирает llms.txt и README-оглавление, печатает отчёт о неразмеченных файлах и битом YAML.
- Запуск: (а) Claude Code при добавлении/правке заметки — основной путь; (б) GitHub Action на push в main — страховка (правки через веб-редактор и мимо Claude Code; защита от само-триггера).

### Масштабирование и запасные ходы

- До ~500 заметок — один корневой llms.txt (60–90 КБ, один fetch). Дальше — двухуровневая схема: корневой файл ссылается на llms.txt разделов.
- **Fallback**: официальный `github-mcp-server` (чтение через `get_file_contents` / `search_code`) — работает независимо от llms.txt.
- **Локальный максимум качества (опция)**: Claude Code / stdio-MCP с папкой базы на маке — grep по рабочей копии для глубоких сценариев. Не входит в v1 как обязательная часть.

## Отложено (не отвергнуто)

- **Write-MCP** (официальный `github-mcp-server`, remote, OAuth) — запись из чата с любого устройства. Подключается, только если резервного пути через веб-редактор станет мало. Собственный write-код не пишется ни в каком варианте.
- **Собственный remote read-MCP** (официальный MCP SDK, `kb_index/kb_search/kb_read`, клон-кэш + ripgrep, хостинг у крупного провайдера). Строится, только если навигация по llms.txt начнёт систематически промахиваться и понадобится полнотекстовый поиск с любого устройства. Вся работа v1 при апгрейде переиспользуется.
- **BM25/эмбеддинги** — только после появления своего read-сервера и доказанной нехватки лексики.
